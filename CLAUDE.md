# Fantasy Football Draft Assistant

## Shell

- **Default to the PowerShell tool for all commands.** The Bash tool often fails on this Windows machine — do not use it unless the owner says otherwise.

## Local Development

- **Primary branch:** `master`

## Running

- Terminal UI: `python -m draft_assistant`
- Desktop UI (Tkinter): `python -m draft_assistant ui`
- Web UI (browser): `python -m draft_assistant web`
- Desktop App (pywebview): `python -m draft_assistant app` (requires `pip install -r requirements-desktop.txt`)
- Tests: `python -m unittest discover tests -v`

## Key Details

- Python 3.10+, no external dependencies for core app
- 728 tests in `tests/`
- Web UI uses hashed, license-inventoried vendored React + in-browser Babel (no build step), with no runtime CDN dependency.
- Player data lives in `data/projections.json` (tracked)
- League config in `league.config.json`
- Named profiles under `.draft_assistant_profiles/<name>/` — gitignored, as is `draft_state.json`

## Packaging

- **One spec, both platforms:** `packaging/DraftAssistant.spec` drives the Windows installer (`packaging/windows/build.ps1` → Inno Setup) and the macOS `.dmg` (`packaging/macos/build.sh`). CI builds all three artifacts via `.github/workflows/release.yml`. Version comes from `draft_assistant.__version__` — bump it there only.
- **Paths are the load-bearing part.** `paths.py::resolve()` returns the plain relative path in a source checkout and an absolute per-user path (`%LOCALAPPDATA%\DraftAssistant`, `~/Library/Application Support/DraftAssistant`) when frozen. An installed app cannot write beside its executable, so **anything that persists state must route through `resolve()`** — hardcoding a relative path works in dev and silently breaks the installed build. `DRAFT_ASSISTANT_HOME` overrides it.
- Tests assert the dev-mode paths verbatim (`tests/test_profiles.py`) and chdir into temp dirs, so `resolve()` must stay a no-op unless frozen.
- Both build scripts smoke-test the bundle (launch it, hit `/api/state`, check seeding) before packaging. That is what catches a missing `--add-data` file or hidden import.
- The packaged app ships the **web UI only** — `tkinter` is deliberately excluded from the bundle, so `draft-assistant ui` stays a source-checkout feature.

## Credentials

- **No plaintext at rest, ever.** `secret_store.py` seals ESPN cookies and Yahoo tokens with DPAPI (Windows) or the login Keychain (macOS). With neither (`backend() == "none"`, e.g. a Linux checkout) they live in the in-process `_session` only, and a legacy plaintext file is moved into memory and **deleted on first read** — a status poll is enough. That deletion is deliberate; doing it silently was the bug. It now prints one `WARNING:` per removed file on stderr, `describe()` says the same to the UI, and `plaintext_removed(path, account)` lets a handler surface it.
- **The marker file names the Keychain item, not the path.** On macOS the store file is only `{magic, backend, account}`; `account` is `<provider>:<uuid4 hex>`, minted on the first save and reused by every later one. 0.7.4 derived the name from a hash of the file's path, so moving or renaming the data directory lost the credential and orphaned the item. Any `<provider>:<hex>` in a valid marker is read wherever the file now sits — do not re-derive a name from the path to "validate" it.
- **`forget()` errs toward deleting.** It removes the item the marker names *and* the name 0.7.4 derived from the path (`_keychain_account`, kept for nothing else), so a 0.7.4 item whose marker was lost is not left behind. Two accepted costs, both pinned by tests: a copied directory is indistinguishable from a moved one (both markers name one item), so forgetting through either copy forgets both; and a 0.7.4 store that was moved still reads the item named after its old path, so forgetting whatever now lives at that old path forgets it too. Either way the other side just authorizes again — a secret left in the Keychain after "forget" is the worse failure.
- **Legacy shared items are copied, never deleted.** 0.7.3 and earlier kept one item per provider under the bare name (`yahoo`), shared by every profile. The first read copies it into a per-store item; other profiles may still point at the original, and a failed migration must leave both it and the marker untouched.
- **Secrets go to `security` on stdin, not argv.** argv is visible to every local process, on every hourly token refresh. `_keychain_write` feeds `security -i` one line: `-X <hex>` when it fits, a single-quoted `-w` (backslash and `'` escaped) when only that fits, and the old argv call when neither does or anything goes wrong. The tool's line buffer is **4096 bytes and an over-long line is split, not rejected** — the first 4095 bytes run (storing a truncated secret) and the rest runs *as the next command* — hence `_KEYCHAIN_LINE_LIMIT = 4000` and `-U` deliberately last. The exit status is only the last command's, so **every stdin write is read back** and a mismatch falls back to argv; that fallback is what keeps the stdin path never worse than the old one. Don't raise from inside an `except` around these calls: `from None` hides the chain but `__context__` still carries the argv.
- None of the Keychain code runs off macOS. The unit tests drive it through `FakeSecurity` (a port of the tool's line reader and tokenizer, in `tests/test_secret_store.py`); only the `macos-keychain` CI job and `scripts/check_native_secret_store.py` touch the real thing.

## Web UI structure

- **Navigation is league-first:** leagues list → **league hub** → either the **draft room** or the **waiver wire**. The two destinations are siblings, never nested: the draft room has no waiver-wire entry point and the waiver wire has no draft controls. `App` in `app-components.jsx` owns the route (`{screen, leagueId}`); there is no router.
- **Script load order matters** (`static/index.html`). Each Babel script gets its own scope, so every file publishes what later files need with `Object.assign(window, …)`. `ui-kit.jsx` is first and owns the design tokens (`T`) plus every shared primitive — `Btn`, `Badge`, `PosBadge`, `Field`/`Input`/`Select`/`SegmentedControl`, `Modal`, `Drawer`, `Menu`, `AppBar`, `EmptyState`, `Note`, `toast`, `confirmDialog`, `useLayout`. Build new UI out of those; don't re-derive a one-off button.
- `static/styles.css` owns what inline styles cannot: the font stack, `:focus-visible` rings, hover/active states, scrollbars, animations, tables, and the menu/toast/dialog CSS.
- **Themes are custom properties; `T` only points at them.** Every `T` entry is a `var(--…)` reference, and `styles.css` defines the values four times: `:root` is Classic, then `:root[data-theme="sleeper"|"espn"|"yahoo"]`. A new token goes in all four blocks (or the theme inherits Classic's value, e.g. a white card in dark Sleeper) and in `T`. Nothing may do arithmetic on a token: no `${T.primary}33` alpha suffix, use `alpha(T.x, 20)` (`color-mix`). No raw `#hex`/`rgb()` in components either: the only exception is the picker swatches, which sit between `theme-literals:start`/`:end` in `ui-kit.jsx`. `node scripts/check_theme_tokens.js` (CI) enforces all of that and holds every text/background pair, position badges and the app bar included, to WCAG AA 4.5:1.
- **Sleeper's primary is its RB colour** (mint `#19d3b5` against teal `#20ceb8`, about 1.02:1), so nothing drawn on top of position fills may be marked with `T.primary` alone. Your seat on the pick ticker and draft board uses `T.seatMark` (`--seat-mark`: primary in Classic, ESPN and Yahoo, white in Sleeper), which `check_theme_tokens.js` holds apart from every `--pos-*-bg`. The ticker's on-the-clock cell is told apart by an `onPrimary` ring, not by its fill.
- **The theme choice is a workspace preference** (`preferences.theme`: `sleeper` (default), `espn`, `yahoo`, `classic` or `match`). It is mirrored to `localStorage.fda_theme`, so the inline script in `index.html` can set `data-theme` before first paint and the dark board never flashes light. `match` resolves in `App` from the open league's `platform` (`resolveTheme`); outside a league, and for platforms with no theme, it falls back to the default. The themes copy each platform's colour, shape and density, never its logos or typefaces. The app bar can be a brand band (ESPN black, Yahoo purple), so anything placed on it uses the `appbar*` tokens, not page colours.
- Static files are served `Cache-Control: no-cache`. Without it the browser kept last version's scripts and stylesheet next to a fresh `index.html`.
- Board rows (`.da-player-row`) take their hover state from CSS, not React state. A hover id in state re-rendered all ~2,200 rows on every pointer move. On phones a row tap opens `PlayerDetailSheet`, because the row tooltips are unreachable on touch screens.
- **No `window.confirm`/`alert`.** Destructive actions go through `confirmDialog(...)` (a promise of a boolean) and outcomes report through `toast(msg, 'ok'|'error'|'info')`.
- `useLayout()` is the single breakpoint vocabulary (`isMobile` < 760, `isTablet`, `isDesktop` ≥ 1140). The draft room's phone header only fits four controls — panels move into the More menu there.
- **News context in the UI:** `/api/players` and `/api/suggest` attach `availability` and `signals` per player, and `/api/free-agents` returns `weeklyRecommendations` + `rosRecommendations` with `points`, `urgency`, and `weeklyProjectionOrigin`. Render availability through `AvailabilityChip` (it abbreviates the feed's spelled-out statuses) and always filter signal lists through `playerNewsSignals()` — raw lists contain `source_updated` entries, which are bookkeeping about the feed and say nothing about the player.
- **A player with no NFL team is the load-bearing "cannot score" signal.** Sleeper reports a released veteran as `status: "Active"` with `injury_status: "Questionable"` and **`team: null`** — status alone cannot tell them apart from a healthy starter, which is how Joe Mixon and Tyreek Hill stayed draftable months after leaving their rosters. `_refresh_sleeper_players` turns a falsy `team` into a `roster_status: "Free Agent"` signal (except `DEF`/`DST`, which legitimately have none); `"free agent"` was already in `INELIGIBLE_ROSTER_STATUSES`, so that one emitter is what makes `is_candidate_eligible` drop them. Never give `roster_status` an `expires` — Mixon's only flag was a 48h injury designation, and once it lapsed he looked perfectly healthy.
- **The eligibility gate fails open**, so absence of signals means eligible. That is backwards for someone out of the league, who generates no news at all — which is why the draft room now shows `contextStale`/`contextFailedSources` from `/api/suggest` and the startup refresh reports failures through `toast` instead of swallowing them.
- **Signals are indexed per context — per-player code goes through `signals_for_player`, never a loop over `context.signals`.** `context.py` groups the list by `player_id` on first lookup, and `is_candidate_eligible`, `primary_availability`, `signal_summary` and the rest all read that. Scanning the list per player is O(players × signals): with a ~6,000-signal news cache it was ~1s of every `/api/suggest` and ~2.5s of `/api/players`. The index checks itself against a copy of the list on every lookup, so appending, rebinding or replacing signals in place needs no invalidation call — and results keep the order of `context.signals`, which `primary_availability` depends on.
- **A stale history is evidence, not a gap.** `historical.py::history_recency_factor` discounts a player whose stats stop before the last completed season, shifting the blend toward the published projection. Don't try to fix this inside `_historical_trend`: it returns a *weighted average*, so scaling every season's weight cancels out and changes nothing.
- `rosterTotal()` (in `shared-utils.js`) is the draftable roster size: it skips `IR`, which is a roster slot but never a draft round. Counting it inflated "N slots" and drew a phantom extra round on the pick ticker.
- **A rejection that replies before reading the body must still drain it.** The server is HTTP/1.0, so it closes after every response — and closing a socket with received-but-unread bytes buffered is an *abortive* close on Windows. The RST makes the client discard the reply it had not read yet, so the 403/413/415 answers went missing on ~3% of requests and made the suite intermittently red. `DraftAPIHandler.finish` drains first (`_linger_close`), gated on `_body_drained`, which only `_read_body` sets. Any new early rejection added ahead of `_read_body` inherits that for free — but don't "simplify" it by draining the claimed `Content-Length`, which is exactly the unbounded allocation the 413 check exists to prevent. `TestEarlyRejectionsCloseCleanly` loops each path 100× because one request usually passes even when this is broken.
- **A season is named for the year it kicked off, and only `context.py` knows what "now" is.** `default_season()` keeps January and February in the previous year's season — week 17 straddles New Year and week 18 follows it — and rolls over on March 1, after the Super Bowl and ahead of the spring pulls for the season about to be drafted. `default_week()` counts Tuesday-to-Monday fantasy weeks from the Tuesday before `season_kickoff()` (the Thursday after September's first Monday): 1 until then, 18 from the end of week 18 to the rollover. On the calendar year, January 1 was week 1 of a season with no games — championship week, with every bye ignored. `free_sources.default_projection_season()` is that same function, so a pull, the CLI's `refresh-byes` and the web repair cannot name different seasons. **`load_context()` is the single reader of the news cache, and the season it returns is the one asked for (today's unless named), never the one in the file.** The cache is one slot: read back with its own season, one left over from last autumn made `/api/players` judge a correctly stamped board against last year, report no byes, and offer a "Load bye weeks" click that re-stamped 1,256 players from last year's schedule. A cache for any other season reads as no news yet (the gate fails open and `contextStale` says so). Nothing may treat the cached season as current: handlers take `load_context().season`, `POST /api/refresh-byes` defaults to that same expression so it stamps exactly what `/api/players` judges, and the startup refresh posts `{}` — echoing `ctx.season`/`ctx.week` back is what pinned both. An explicit `season` in a request still means that season. The browser has exactly one copy of the rule, currentNflSeason() in shared-utils.js, for the Pull Data and ESPN import forms that need a season before any request is made; scripts/check_league_sync.js pins it to the same anchor dates as 	ests/test_season_calendar.py. Nothing else may default a season to the calendar year: history_recency_factor and the CLI collectors did (the CLI even hard-coded 2026) until 	ests/test_season_defaults.py pinned them.

## Platform leagues

- **Import + roster sync:** ESPN (`importers/free_sources.py`, public leagues), Yahoo (`importers/yahoo.py`, OAuth), Sleeper (`importers/sleeper.py`, public API — no auth). All three land on `POST /api/sync-league`, which maps provider rosters to board players via `platform_sync.py`.
- **Matching** is by stable `Player.id` or provider metadata first, then name+position fuzzy. Sleeper rosters carry only ids, which is why id-only matching must keep working — don't reintroduce a name/position guard before the provider lookup in `_PlayerMatcher.match`.
- **Draft picks and current ownership are two different records.** `picks` is draft history (the draft room's board); `league.rosterSnapshot` is who owns whom *right now* (the waiver wire's input). Adds, drops, trades and undrafted pickups mean the two diverge the moment the season starts — reading picks as ownership is what recommended MarShawn Lloyd while he sat on someone's bench. The league hub's Sync writes only the snapshot; the draft room fills `picks` from `/api/draft-sync` on its own. `rosterSyncKey(league)` fingerprints the provider/season/seat mapping, and `preserveRosterSnapshot` drops a snapshot whose fingerprint no longer matches, so a re-linked league can never rank against stale ownership.
- **The saved snapshot is a labelled fallback, and only for a sync that failed.** The waiver wire syncs live on every visit; when that sync *errors* (provider down, Yahoo token lapsed) it used to show the error and rank nothing, an hour-old snapshot sitting unused beside it. `fallbackRosterSnapshot(league)` (next to `rosterSyncKey`) is the whole decision: the snapshot's `leagueKey` must equal `rosterSyncKey(league)`, it must hold players, and its `syncedAt` must parse — because the screen has to say "rosters as of …" in a warning that does not scroll away, in the AppBar subtitle and on the roster panel, until a retry succeeds. Never widen it to a sync that *succeeded*: zero players from a live sync is authoritative, while a saved empty snapshot is refused (it would put every owned player on the wire and leaves no roster to rank against). Unlabelled stale ownership is still the bug. Any waiver re-rank that waits on the network first (a news refresh, a bye-week reload) must go through `rescan`, which runs the scan of the latest render: the `scan` a click closed over still holds that render's rosters, and re-ranking with it after a Retry that succeeded put the saved rosters back on screen with the label already cleared.
- **`POST /api/free-agents` takes `rosters`, not `picks`.** A league linked to a provider **must** supply current roster entries (from the request, or a saved `rosterSnapshot`) — falling back to draft history is a hard 400, because silently ranking against picks is the bug, not a degraded mode. Only unlinked manual leagues may still use `picks` as their ownership record. An empty roster list is authoritative, never a reason to resurrect a saved snapshot. The failed-sync fallback does not bend that: the browser decides, labels it, and sends the snapshot's entries as `rosters` itself — the server is never the one to prefer a snapshot over what the request says.
- **Ownership must survive a player the board has never heard of.** `synced_rosters_to_picks` keeps an unmatched or duplicate-resolving roster entry as a placeholder carrying `providerPlayerId`/`sourceName`/`sourcePosition`/`sourceTeam` and `unmatched: true` — never `continue`, or a rostered player with no projection reads as a free agent. `resolve_roster_entries` re-resolves those placeholders against today's board on every scan (without mutating the stored snapshot), so a later data pull quietly upgrades them. For the same reason the provider parsers keep id-only rows: a missing name or position is not evidence the player is unowned.
- **Bench, IR, reserve and taxi are roster spots.** Sleeper's `reserve` and `taxi` lists sit beside `players`, and ESPN/Yahoo mark reserve slots rather than omitting them — every one of those players is unavailable on waivers, so all of them must reach the snapshot.
- **Sleeper live draft sync** (`POST /api/sleeper/draft`) is the only real-draft feed: Sleeper publishes actual pick numbers and seats, so `synced_draft_to_picks` returns true picks and `draft-screen.jsx` polls it every 5s behind the "Go Live" button. **Every pick must survive to the output list.** The UI reads the next pick as `picks.length + 1`, so dropping one shifts the clock for the rest of the draft. Both an unmatched player *and* a second pick that resolves to an already-taken board player become placeholders — never `continue`.
- **A pasted Yahoo settings page has to prove it was one.** Every value `yahoo.parse_settings_text` returns has a default behind it, so the finished result cannot say whether anything was read: `lorem ipsum` used to import as a 10-team league named after its own first line. Each section now adds to `recognized` (a labelled league-name row, team count, draft type, a roster position, a scoring row) and an empty set is a `ValueError`, which the handler returns as a 400 telling the user what to paste. A partial paste still imports — the scoring table alone, or the roster alone, with defaults for the rest — so a new section must add to `recognized` or pastes holding only that section start being refused. The row-start checks run over `row_text` (the `splitlines()` view), because `^` only breaks on `\n` while the rest of the parser splits on every line break.

## Data pulls

- **Full Collect is a superset of Free Sources, not an alternative.** `collectors/combined.py::collect_all_result` runs `pull_free_data` first — that is the player pool — then `_absorb`s `nfl_data_py` and Sleeper's season-stats archive onto it. It used to be a separate, narrower pipeline (nflverse rosters ∪ Sleeper only), which is how "Full" came back ~450 players *smaller* than "Free" on the same board. Enrichment must only ever add: never rebuild the pool from an enrichment source.
- Both `/api/pull-free-data` and `/api/collect-all` take the same request body and both must route their save through `update_players` + `merge_historical_into`. Calling `save_players` directly drops every stats season an earlier pull banked — the CLI did exactly that until `cmd_pull_free_data` was fixed, silently replacing a 2023/24/25 board with 2025 only. An explicit `--out` is an export and still writes verbatim.
- **ESPN needs no league id.** `_espn_player_url` falls back to `leaguedefaults/3`; a league only decides how stats are *scored*, so the raw `statSourceId=1` lines are identical either way. That is also what makes ESPN gradeable — a personal league 401s for seasons before it existed, the default reaches back to 2019 (2023 excepted: ESPN serves a ~86-player stub, see `backtest.ESPN_SPARSE_SEASONS`).
- **`SOURCE_WEIGHTS` is earned, not assumed.** `backtest.calibrate_source_weights` blends stat lines across six seasons and three scorings, compares only players *both* sources projected, and leave-one-season-out validates against an even split. Only RB and TE justified a tilt; QB and WR got *worse* when weighted. Don't read a raw source-vs-source table as a weighting argument — ESPN looks far better at WR there purely because it projects ~59 receivers to FFToday's ~38, and coverage already pays off by ESPN being in the pool. Sleeper stays neutral because its archive is revised in-season and cannot be graded at all.
- `_align_names` renames a near-miss enrichment record onto the pool's spelling before merging, so "Deandre Swift" enriches "D'Andre Swift" instead of landing beside it. Merge keys come from `free_sources._merge_key` (team code for DST, compact normalized name otherwise) — keep both sides on that one function.
- `free_sources._merge_player` is the single gap-fill merge. Anything added to `Player` needs a line there or it silently vanishes whenever two sources describe the same player.
- **Yahoo leagues pull their own room's ADP.** A pull whose body carries `yahooLeagueKey` (the UI sends it for Yahoo-imported leagues) overlays `yahoo.fetch_draft_analysis` — the league's `draft_analysis`, real average picks from actual Yahoo drafts — onto the board via `free_sources.apply_yahoo_adp`: `Player.adp` becomes the Yahoo number, the public board's value moves to `metadata["public_adp"]`, and `yahoo_adp`/`yahoo_avg_cost`/`yahoo_percent_drafted` land in metadata. Requires the saved Yahoo OAuth token; failures surface as a not-ok "Yahoo ADP" source report and never sink the pull.
- **Scraped sources share `importers/_scrape.py`** — the nested-table parser (fantasy sites still use layout tables, and a single-buffer parser scrambles them), the retrying fetch, and the number/name helpers. `fftoday.py` keeps a thin `_fetch_once` of its own purely so tests can patch its fetcher; the retry itself lives in `_scrape`. Match columns by header text like `cbs.py` does where the site allows it — FFToday's fixed offsets exist only because it labels passing and rushing yards identically.
- **Only CBS was scrapeable, and that was checked, not assumed.** FantasyPros server-renders 10 players per position and serves the rest from `/api/`, `/ajax/`, `/json/` — all three robots-disallowed, so there is no permitted way to get a full table. NFL.com's projections page is a client-side app with zero `<tr>`. CBS ships whole tables on a robots-allowed path (it disallows `sortcol`/`sortdir`, so keep those out of the URL). Re-check robots before adding another site.
- A scraped source that returns **zero rows** has usually been redesigned rather than gone down, so `fetch_all_cbs` raises on an empty parse and the single-source warning names a site that returned nothing — silence is the failure mode to design against.
- **A bye without `bye_season` is a bye the engine ignores.** `current_bye_week` trusts `bye_week` only when `metadata["bye_season"]`/`["bye_team"]` match, so the seed board has to carry the stamp: 0.7.4 shipped one saved before pulls wrote it, with 1,325 bye weeks and not one in use (no draft bye penalty, no bye on the waiver wire). `python -m draft_assistant refresh-byes [--season N]` re-stamps a saved board from the schedule through the same `apply_schedule_byes` the pull uses, and touches nothing but the bye fields — so a preseason board never has to be re-pulled, and its projections and ADP replaced with in-season numbers, just to fix byes. An install keeps its own board and the packaged app has no terminal, so the same repair (`free_sources.refresh_board_byes`) is also `POST /api/refresh-byes` — inline rather than a task, so an unpublished schedule comes back as a 502 the UI can show and the board stays byte-identical — and `ByeWeeksNotice` offers it in the draft room and on the waiver wire whenever the loaded board has players but no `byeWeek` at all (`boardLacksByes`), reloading through the same `refreshPlayers` a finished Pull Data calls. The release gate (`data_quality.py`) counts *verified* byes and fails when players on an NFL team carry a stored bye the engine would ignore; it judges them against the board's own season (the newest `bye_season` it carries), never `date.today()` — it runs offline on every PR, and against the calendar the same board would turn red each New Year until the next schedule is published.

## Recommendation engine

- **One engine, all UIs:** `draft_assistant/rollout.py` (`rollout_values`) ranks the board by a rest-of-draft Monte Carlo rollout — each player's score is the expected effect of drafting them now on your **total season points**, accounting for who survives to your later picks (positional opportunity cost). `suggest.py` delegates to it.
- **Web/desktop app** call it over HTTP via **`POST /api/suggest`** (`web/server.py::_handle_suggest`); `draft-screen.jsx` renders the result. The old client-side `scoring-engine.js` is retired (not loaded); `opponent-model.js` is kept for the Opponents panel only.
- Servers are `ThreadingHTTPServer`: `/api/suggest` on the 2,209-player board takes ~2.5s at the default 48 sims (~1.5s at 24), nearly all of it the rollout, and a single-threaded server froze the UI for that long.
- Only the leading `rollout_candidates` players (default 16) get a full rollout. Keep the sim pool decoupled from `top_n` — tying them together made every extra board row cost a full set of simulations.
- The remaining requested rows come back with `simulated: false` and **`impact: null`**, and the board shows them as `—`. Don't be tempted to surface the prelim score there instead: a simulated impact compares two *completed* rosters, while a prelim row only knows what the player adds to the roster as it stands, so the two differ by roughly the value of every remaining pick (~1800 pts in a 17-round league). There is no cheap rescaling — closing that gap is what the simulation does.
- **Replacement level is priced off *remaining* league demand.** `replacement_levels(..., occupied_players=...)` subtracts already-drafted players from league-wide starter slots; without it the baseline sank deeper every round and inflated VOR. Two consequences worth knowing: once a position's starter demand is satisfied its replacement becomes the best available player (so VOR stops discriminating there — normal from roughly round 8 on), and **every drafted player must reach that argument**. Callers resolve picks against the board, so an unmatched `name|POS` pick would be filtered out — `rollout.py::_unmatched_board_players` re-synthesizes those from `state.picks`, mirroring what `_unmatched_roster_players` does for your own roster.
- Everything is config-driven (teams/roster/scoring per league). Tunables live in `config.draft`: `rollout_sims`, `rollout_candidates`, `adp_noise`.
- **The lineup is assigned twice, and one fixture file pins the two together.** `slot_assignment.py` does it for the engine; `buildLineup`/`getRosterNeeds` in `shared-utils.js` do it again for the draft room's team panel and the waiver roster panel. `tests/fixtures/lineup_parity.json` (generated from the Python side, never hand-edited) is the contract: `tests/test_lineup_parity.py` fails when the file is stale and checks every case against an exhaustive search, and `scripts/check_lineup_parity.js` replays the same file through the browser code. Both run in CI. After an intended engine change regenerate with `python -m tests.test_lineup_parity --write`, then re-run the Node check. Projections within a case are distinct on purpose: with ties the two sides may legitimately seat different equal-valued players, and the last bench seat is only defined when the cut falls between different bench values.
